# DL-CBOR v1

Status: Phase 0 draft. No bytes described here may be written to a durable
Datalevin store until the Phase 0 performance gate and the complete JVM/Rust
golden-corpus gate pass.

DL-CBOR is Datalevin's restricted, platform-neutral value encoding based on
CBOR. RFC 8949 defines the underlying representation. This document narrows
that representation so independent implementations produce the same bytes and
host-language classes do not become part of the format.

The normative artifacts for this draft are:

- this document;
- [`v1.cddl`](v1.cddl), for the structural grammar;
- [`golden-vectors.tsv`](../../resources/datalevin/cbor/v1/golden-vectors.tsv),
  for exact valid bytes; and
- [`malformed-vectors.tsv`](../../resources/datalevin/cbor/v1/malformed-vectors.tsv),
  for invalid bytes, decoder mode/limit profiles, and exact error codes.

The provisional extension artifacts are
[`draft-extension-vectors.tsv`](../../resources/datalevin/cbor/v1/draft-extension-vectors.tsv)
and
[`draft-extension-malformed-vectors.tsv`](../../resources/datalevin/cbor/v1/draft-extension-malformed-vectors.tsv).
They contain the compact scalar byte strings and the remaining tagged
extensions. The latter still use an unassigned stand-in tag and must be
regenerated with an assigned tag before becoming normative.

The prose rules take precedence where CDDL cannot express determinism,
duplicate rejection, resource limits, or host-value normalization.

## 1. Encoding modes

Canonical mode has exactly one encoding for each supported semantic value. It
is required for storage keys, DUPSORT values, identity hashes, and golden
fixtures. Canonical writers and validating readers:

- use definite lengths;
- use the shortest integer, tag, and length arguments;
- sort map keys by canonical encoded-key length and then unsigned lexical byte
  order;
- sort set members by the same rule;
- reject duplicate canonical map keys and set members;
- encode semantic float32 as float32 and semantic float64 as float64;
- use the canonical quiet-NaN bits `0x7fc00000` and
  `0x7ff8000000000000`, respectively;
- preserve the sign of zero; and
- reject malformed UTF-8, unsupported simple values, indefinite-length items,
  and trailing bytes after a single item.

Fast mode retains definite lengths, shortest scalar forms, and every type
distinction, but may retain the input iteration order of maps and sets. A Phase
0 measurement decides whether fast mode is needed outside identity-bearing
contexts.

## 2. Core values in the initial corpus

| Semantic value | Representation | JVM result |
| --- | --- | --- |
| null and booleans | CBOR simple values | `nil`, `Boolean` |
| signed 64-bit integer | CBOR major type 0 or 1 | `Long` |
| larger integer | tag 2 or 3 with a minimal unsigned magnitude | `clojure.lang.BigInt` |
| float32 | CBOR float32 | `Float` |
| float64 | CBOR float64 | `Double` |
| decimal | tag 4, `[exponent, mantissa]` | normalized `BigDecimal` |
| ratio | tag 30, `[numerator, denominator]` | normalized Clojure ratio/integer |
| bytes | CBOR byte string containing `FE` followed by the raw bytes | `byte[]` |
| text | valid UTF-8 CBOR text | `String` |
| vector | CBOR array | Clojure persistent vector |
| map | CBOR map | Clojure persistent map |
| set | tag 258 containing an array | Clojure persistent set |
| URI | tag 32 containing text | `java.net.URI` |
| UUID | tag 37 containing exactly 16 network-order bytes | `java.util.UUID` |
| millisecond instant | tag 1001 containing the restricted RFC 9581 map | `java.util.Date` |
| unsigned 16-bit array | RFC 8746 tag 69 containing little-endian bytes | `char[]` |
| signed 16-bit array | RFC 8746 tag 77 containing little-endian bytes | `short[]` |
| signed 32-bit array | RFC 8746 tag 78 containing little-endian bytes | `int[]` |
| signed 64-bit array | RFC 8746 tag 79 containing little-endian bytes | `long[]` |
| float32 array | RFC 8746 tag 85 containing little-endian bytes | `float[]` |
| float64 array | RFC 8746 tag 86 containing little-endian bytes | `double[]` |
| keyword | byte string with subtype `FB` or `E0` | Clojure `Keyword` |
| symbol | byte string with subtype `FC` or `E1` | Clojure `Symbol` |
| UTF-16 character | byte string with subtype `E2` | `Character` |
| Java regular expression | byte string with subtype `E3` | `java.util.regex.Pattern` |
| list | draft Datalevin extension 4 | Clojure persistent list |
| queue | draft Datalevin extension 5 | Clojure persistent queue |

Java `Byte`, `Short`, `Integer`, and `Long` inputs normalize to a signed
64-bit integer and decode as `Long`. A native integer outside that range is not
valid DL-CBOR: writers use bignum tag 2 or 3 instead.

A decimal is normalized by removing redundant powers of ten. Zero is encoded
as exponent zero and mantissa zero. Thus `1.0`, `1.00`, and `1M` have identical
bytes. The exponent must fit a signed 32-bit value after normalization.

A rational numerator and denominator are integers. The denominator is
positive, the greatest common divisor is one, and zero has denominator one.

A URI is encoded in its non-empty ASCII form. JVM writers use
`URI.toASCIIString`; a neutral implementation rejects a non-ASCII URI value
that has not yet been normalized.

Text must contain Unicode scalar values. A JVM string containing an unpaired
UTF-16 surrogate is rejected rather than replaced during UTF-8 encoding.

A millisecond instant uses the extended-time form from RFC 9581 tag 1001. Its
map contains key `1` with whole POSIX seconds and, only when needed, key `-3`
with an unsigned remainder from 1 through 999. Writers use floor division, so
`-1` millisecond is `{1: -1, -3: 999}`. No other extended-time keys are valid
DL-CBOR v1. JVM `Date` and `Instant` inputs normalize to `Date` at millisecond
precision.

Primitive arrays use the RFC 8746 little-endian variants because every
currently supported Datalevin CPU is little-endian and the representation can
therefore support future bulk-copy paths. A `byte[]` uses the `FE` subtype
described below. The v1 primitive-array set is `char[]`, `short[]`, `int[]`,
`long[]`, `float[]`, and `double[]`; `boolean[]` is not a numeric typed array.
Payload length must be a multiple of element width and the element count is
subject to the collection limit. Float-array NaNs use the same canonical quiet
NaN bits as scalar floats in both writing modes; signed zero is preserved.

### 2.1 Byte-string subtypes and named values

At every DL-CBOR value position, a CBOR byte string starts with one subtype
byte. These are local DL-CBOR codes, not CBOR semantic tags. `FB`, `FC`, and
`FE` reuse the existing typed-data headers; the surrounding byte string and
the compact name payload rules are specific to DL-CBOR.

| Subtype | Value | Remaining byte-string contents |
| --- | --- | --- |
| `FB` | unqualified keyword | UTF-8 name |
| `FC` | unqualified symbol | UTF-8 name |
| `E0` | qualified keyword | namespace byte length, UTF-8 namespace, UTF-8 name |
| `E1` | qualified symbol | namespace byte length, UTF-8 namespace, UTF-8 name |
| `E2` | UTF-16 character | shortest one- or two-byte unsigned big-endian code unit |
| `E3` | Java regular expression | shortest unsigned LEB128 flags, UTF-8 source |
| `FE` | ordinary bytes | arbitrary raw bytes, possibly empty |

The namespace length is an unsigned LEB128 integer, not a nested CBOR item:
seven low bits per byte, least-significant group first, with the high bit set
when another group follows. It is in `0..2147483647` and uses its shortest
encoding in both modes. Lengths 0 through 127 occupy one byte, 128 through
16383 occupy two, and larger lengths occupy up to five. A redundant high
zero group is `NON_SHORTEST`; a value above the bound or a fifth continuation
byte is `LENGTH_OUT_OF_RANGE`.

The length counts UTF-8 **bytes**, not characters or UTF-16 code units. The
outer byte-string length supplies the end of the name, so no name length or
namespace separator is stored. Each text segment must independently be valid
UTF-8 containing Unicode scalar values; splitting a code point at the
namespace boundary is `INVALID_UTF8`. Literal NUL and slash need no escaping.
An unqualified header means an absent namespace; a qualified header with zero
namespace length means a present empty namespace. Empty names are allowed.
Decoders construct namespace and name separately rather than parsing a joined
string.

An empty outer byte string, unknown subtype, missing/unterminated namespace
length, or namespace length beyond the remaining body is `INVALID_EXTENSION`.
A physically truncated outer byte string remains `TRUNCATED`. These rules
also apply to fast decoding. The old tagged keyword/symbol/character/regex
IDs 1, 2, 3, and 6 are retired and rejected by writers and readers, preventing a second wire
representation of the same value.

Examples, including the CBOR byte-string head:

```text
:a        42 FB 61
:user/id  48 E0 04 75 73 65 72 69 64
symbol a  42 FC 61
bytes []  41 FE
bytes [FB 61]  43 FE FB 61
```

Byte strings required as the immediate contents of standard bignum, UUID, and
numeric-array tags retain their standard raw payloads and contain no DL-CBOR
subtype. Nested DL-CBOR values, including values inside extension arguments or
unknown forwarding tags, use the subtype rules above.

### 2.2 Characters

A character is one unsigned UTF-16 code unit in `0..65535`, including isolated
surrogates. It is not encoded as UTF-8 text. Subtype `E2` is followed by one
byte for values in `0..255`, otherwise two bytes in big-endian order. The outer
byte-string length determines the width; no additional length or integer head
is stored. Zero is encoded as one `00` byte.

The byte-string body must contain two or three bytes including the subtype;
other widths are `INVALID_EXTENSION`. A two-byte code unit with a zero high
byte is `NON_SHORTEST` in both decoding modes. Character values consume one
scalar depth level and preserve their distinct identity from integers and
strings.

```text
character a       42 E2 61
character U+00FF  42 E2 FF
character U+0100  43 E2 01 00
surrogate D800   43 E2 D8 00
```

### 2.3 Java regular expressions

Subtype `E3` identifies the `java.util.regex.Pattern` syntax family at
Datalevin's Java 17 compatibility baseline. Its payload is a shortest unsigned
LEB128 flag bitmask followed by the exact UTF-8 pattern source. The outer
byte-string length bounds the source, which may be empty and may contain NUL.
There is no separate syntax ID, source length, or source CBOR text head.
A different regex syntax family requires a different subtype.

Writers compute the source's UTF-8 byte length and write directly to the
destination. No intermediate payload array is required. Readers validate
flags before source UTF-8. Missing or unterminated flags, integer overflow,
or undefined/disallowed flag bits are `INVALID_REGEX`; non-minimal flag
varints are `NON_SHORTEST` in both modes. Invalid UTF-8 is `INVALID_UTF8`.
These flags retain the existing semantic contract:

| Bit | Java flag |
| ---: | --- |
| 1 | `UNIX_LINES` |
| 2 | `CASE_INSENSITIVE` |
| 4 | `COMMENTS` |
| 8 | `MULTILINE` |
| 16 | `LITERAL` |
| 32 | `DOTALL` |
| 64 | `UNICODE_CASE` |
| 256 | `UNICODE_CHARACTER_CLASS` |

No other bits are legal. `UNICODE_CHARACTER_CLASS` implies
`UNICODE_CASE`, so canonical flags containing bit 256 also contain bit 64.
`CANON_EQ` (bit 128) is deliberately excluded: the
[Java 17 API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/regex/Pattern.html#compile(java.lang.String,int))
documents that compiling it can exhaust memory for sufficiently many combining
marks. The JVM reader compiles a validated value to `Pattern` and reports
`INVALID_REGEX` for bad Java syntax; the Rust value model retains `source` and
`flags` without claiming to execute Java regex semantics.

```text
/a+/ flags 0      44 E3 00 61 2B
/a/ flags 2       43 E3 02 61
/a/ flags 320     44 E3 C0 02 61
empty pattern    42 E3 00
```

### 2.4 Remaining extension envelope

Native CBOR arrays represent vectors only. List, queue, boolean-array,
sorted-collection, and Datalevin-specific identities require the DL-CBOR
extension envelope. The currently implemented tagged built-ins are list and
queue; the other collection contracts remain pending.

The Phase 0 envelope uses CBOR tag 17484 (`0x444c`) only as a non-durable
stand-in. That tag was unassigned in the IANA registry when this draft was
written; this is not an allocation or permission to persist it. The final tag
must be assigned before release, and every tagged extension vector must then
be regenerated and reviewed.

The tagged item is one flattened, definite-length array:

```text
DL_EXT([type-id, argument-0, ..., argument-n])
```

Flattening avoids a second array header for extensions whose natural payload
is already a sequence. Built-in type IDs are non-negative integers. Open
extensions use a globally unique, non-empty text ID; parsing one never performs
classpath lookup or code execution. An integer ID is limited to signed 64-bit
positive range so the JVM and Rust data models agree. Unknown IDs decode to a
neutral extension value in the Phase 0 forwarding implementation.

| ID | Value | Arguments after the ID |
| ---: | --- | --- |
| 1, 2, 3, 6 | retired scalar IDs | rejected; use byte-string subtypes |
| 4 | list | zero or more list elements |
| 5 | queue | zero or more queue elements in dequeue order |

All arguments recursively obey the selected encoding mode.

## 3. Collection identity

Concrete map/set implementations and custom comparators are never serialized.
Canonical ordering compares complete encoded items, not host-language values.

DL-CBOR type identity is finer than Clojure collection equality in a few
cases. For example, Clojure sets and maps cannot retain an empty vector and an
empty list as distinct members/keys, and they equate signed floating-point
zero even though DL-CBOR preserves its sign. The Phase 0 JVM writer and reader
reject any wire-distinct members or keys that would collapse during Clojure
materialization, using `DUPLICATE_SET_MEMBER` or `DUPLICATE_KEY`; silent loss is
never permitted. Portable cross-language generators exclude such pairs. Before
v1 is frozen, this representability restriction must either become a common
JVM/Rust rule with shared malformed vectors or be replaced by a JVM collection
representation that preserves DL-CBOR identity.

## 4. Storage collision escape

Existing Datalevin typed encodings remain unchanged. Only untyped `:data`
payloads use DL-CBOR.

Typed values currently begin with one of `c0`, `c1`, or `f1` through `fe`.
Some valid bare CBOR values begin with the same byte: notably false (`f4`),
true (`f5`), null (`f6`), float32 (`fa`), and float64 (`fb`). For an untyped
storage field only, prefix `ff` when—and only when—the bare DL-CBOR first byte
is a typed header. The prefix is removed before CBOR decoding. `ff` is the CBOR
break byte and is invalid as a standalone definite-length DL-CBOR item, so the
wrapper is unambiguous.

The `storage_hex` column of the golden corpus is normative for this wrapper.
It does not apply to wire messages, files, or nested values.

## 5. Decoder baseline limits

Every entry point must make limits explicit. The Phase 0 defaults are:

| Limit | Default |
| --- | ---: |
| input item | 64 MiB |
| nesting depth | 256 |
| collection or map entries | 1,000,000 |
| one text or byte string | 16 MiB |
| bignum magnitude | 4 KiB |
| one extension body (compact scalar or tag content) | 16 MiB |

Lengths are checked before allocation. The extension budget begins with the
tag content's array header and includes its type ID and arguments, but not the
outer tag head. Implementations may apply lower limits at a narrower storage or
protocol boundary. A total-allocation budget will be added with framing work.

For compact keywords, symbols, characters, and regexes, the extension budget
includes the entire byte-string body (subtype and payload fields), but not the
outer byte-string head. The byte-string budget also includes that entire body;
`FE` raw bytes are subject to that string budget rather than an additional
extension budget. Each compact value is one scalar item for depth accounting.

## 6. Draft evolution

The settled corpus covers standard-tag values, date/instant boundaries, all
selected primitive numeric arrays, malformed forms, and the storage escape.
The 2026-09-04 draft revision replaces ordinary raw byte strings with subtype
`FE` and moves keywords, symbols, characters, and regexes from the tagged
envelope to compact byte strings. These changes affect non-durable Phase 0 bytes only. Once v1 freezes,
the corpus becomes append-only. A separate provisional corpus covers compact
scalars, the remaining envelope, and every supported regex flag. Before v1 is
released, the assigned-tag version of the remaining envelope must cover every
extension and remaining maximum-boundary case listed in
[`cbor.md`](../../cbor.md).
