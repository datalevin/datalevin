## Abstract

Flexible entity-attribute-value (EAV) stores simplify data modeling but make
cost-based optimization difficult: relational histograms do not naturally
capture entity-centered patterns, correlations, or directional graph fanout.
We present the storage-aware optimizer in Datalevin, a durable Datalog system.
Datalevin organizes EAV and AVE data as nested ordered indexes whose count and
rank operations provide cheap, current cardinalities for point and range
predicates. Remaining join uncertainty is addressed with query-local sampling,
directional fanout estimates, empirical-Bayes shrinkage, and skew-aware
correction. These estimates feed a graph-oriented physical plan in which
entity-centered patterns are executed by merge scans. A
Selinger-style optimizer dynamically switches from exhaustive to greedy
enumeration and selects among indexed directional joins, bitmap-filtered hash
joins, and semi-joins. On a 277.9-million-datom translation of the Join Order
Benchmark, Datalevin executes all 113 queries in 71.8 seconds, versus 171.3
seconds for PostgreSQL 18 in our current run. These results suggest that a
flexible durable store can obtain effective cost-based plans without
conventional offline histograms.

## 1. Introduction

Datalog systems pair a compact declarative language with a flexible data model.
In Datomic-style systems, facts are datoms `(entity, attribute, value)` rather
than fields in fixed-width rows. Applications can add attributes without table
migrations, compose queries from data patterns and rules, and traverse
relationships in either direction. These properties make Datalog a useful
application query language and a promising target for generated queries.

The same representation creates an optimizer problem. A logical object that
would occupy one relational row is spread across several datoms. A query over
several object types initially appears to contain many self-joins, while
foreign-key-like relationships are interleaved with ordinary values. The
optimizer must estimate selective attribute predicates, correlations among
attributes of one entity, and fanout across relationships. Conventional
per-column histograms are a poor fit for this structure. Richer statistics can
be expensive to construct, refresh, and combine, and independence assumptions
can compound rapidly in the cyclic, skewed graphs found in real data.

Datalevin takes a different route: it treats the storage engine as an online
source of query-specific statistics. Its nested EAV and AVE indexes are ordered
and countable. A point lookup such as `[?e :person/country "US"]` has a count
available from the duplicate list, and a value range can be counted using
order-statistics metadata without scanning its results. These counts are exact
for the current database snapshot. Where counts alone do not reveal
correlation or relationship fanout, the planner samples the exact index ranges
named by the current query. This division of labor avoids maintaining
traditional histograms while specializing estimates to the predicates that
actually occur.

Statistics are only one part of the design. Before enumerating plans, Datalevin
recognizes all attribute patterns centered on one entity variable and compiles
them into a single merge scan over the EAV index. The optimizer therefore plans
over a smaller graph of entity stars and relationship edges, not over every
datom pattern independently. It then enumerates connected left-deep plans,
estimates relationship directions separately, and chooses physical operators
that exploit the same indexes used for estimation.

This paper makes three contributions:

1. It describes how nested, countable EAV/AVE indexes provide exact point and
   range cardinalities cheaply enough to use during planning.
2. It presents a hybrid estimator that supplements these counts with
   query-local samples, directional fanout measurements, empirical-Bayes
   shrinkage, and skew-aware correction.
3. It reports systems experience integrating these estimates with a
   Selinger-style Datalog optimizer and several physical join strategies on all
   113 queries of the Join Order Benchmark (JOB) over 277.9 million datoms.

“Without histograms” in the title means without conventional offline value
histograms or multidimensional histograms. Datalevin does retain lightweight
background metadata, including default selectivity ratios, as a fallback. The
central claim is that current index counts and query-local observations carry
the main planning burden.

## 2. Countable Storage as Optimizer Statistics

### 2.1 Nested ordered indexes

A literal triple index repeats long prefixes. In EAV order, every attribute and
value repeats its entity; in AVE order, an attribute and value prefix may occur
with many entities. Datalevin builds on LMDB's `DUPSORT` facility, which maps
one key to an ordered duplicate list. The result behaves as a nested B+ tree:
the outer tree stores a shared prefix and the inner tree stores the remaining
components. Page-prefix compression in the underlying storage layer removes
further redundancy. In the current implementation this representation reduces
triple-index space by about 20%, with a further reported reduction of about 10%
from prefix compression [**replace with controlled space experiment or soften
for the final paper**].

The layout also exposes the quantity an optimizer needs most. For an AVE point
predicate `[?e :a v]`, the number of matching entities is the duplicate count
at key `(:a, v)`, available in constant time. For an interval predicate, such
as a production year between 2005 and 2010, rank metadata in the ordered index
provides the range cardinality in logarithmic time. EAV counts handle a known
entity and attribute. Counts are capped when the optimizer only needs to know
which predicate is smallest, limiting unnecessary work.

Unlike a periodically refreshed histogram, an index count describes the
database snapshot being queried. This matters in a durable system with
continuous updates: there is no window in which the data and its primary
selectivity evidence disagree. Datalevin nevertheless validates a reported
zero against the index before treating the entire query as empty. This
defensive check reflects a useful implementation principle: an inaccurate
estimate may produce a slow plan, whereas a false zero changes the answer.

### 2.2 Predicate pushdown and base cardinalities

The query compiler rewrites single-variable inequalities into index bounds and
pushes eligible functions into attribute scans. It also substitutes constant
inputs before planning. Consequently, the count and the later scan describe
the same restricted key range. This tight correspondence avoids a common
source of estimator mismatch in which statistics describe a column but
execution applies a more complex predicate.

For each entity star, the optimizer counts its bound and free attribute
clauses, chooses the most selective path as the initial scan, and records counts
for the alternatives. Small base relations can be executed during planning;
large ones are represented by a bounded sample. This thresholded policy keeps
planning work proportional to the evidence required rather than the size of
the database.

### 2.3 Query-local sampling

Counts establish marginal selectivity, but do not reveal whether several
attributes co-occur on the same entities or how many target entities a
relationship reaches. Datalevin samples from the concrete ranges identified
for the current query. A sample of entity IDs is passed through the same merge
scan and predicates that execution will use. The surviving fraction estimates
the selectivity of the complete star, including local correlations.

Relationship estimates are directional. Suppose the current plan contains
entities `A`, and a reference attribute links `A` to `B`. Expanding stored
forward references, looking up reverse references, and joining equal values
can have very different fanouts even though they correspond to the same
logical edge. The estimator therefore samples the actual direction and
physical access path under consideration. It records both the mean fanout and
dispersion. An empirical-Bayes estimate shrinks a small or noisy sample toward
a durable fallback ratio, with the prior weighted more heavily as the sample's
coefficient of variation grows. A skew correction also considers an upper
confidence bound, preventing a deceptively calm mean from selecting a
catastrophic high-fanout path.

This is not a claim that sampling eliminates estimation error. Samples can miss
rare heavy hitters and estimates across later joins remain dependent. The
claim is narrower: ordered indexes make it practical to ask query-specific
questions during planning, and shrinkage provides a controlled fallback when
the answers are noisy.

## 3. Simplifying and Planning the Query Graph

### 3.1 Entity stars and merge scans

Several patterns with the same entity variable are not independent relations
in the physical store. For example, fetching a title's name, year, and kind
means locating candidate title IDs and then reading several adjacent
attributes. Datalevin groups these patterns into an entity star. Its merge-scan
operator walks candidate entity IDs in order and scans the requested
attributes in attribute order, applying predicates as values are encountered.
This resembles a pivot scan: it produces a relation for the logical object in
one coordinated EAV walk instead of materializing and joining one relation per
attribute.

Collapsing stars changes both execution and optimization. A query with dozens
of datom patterns may become a small graph whose nodes are entity types and
whose edges are references or shared values. The optimizer no longer
enumerates permutations of joins that merge-scan execution will never
materialize. It instead chooses a starting star and an order and direction for
crossing the remaining graph edges.

This normalization is architectural context, not a novelty claim. Pivot scans,
characteristic sets, and structure-aware RDF planning establish closely related
ideas [2, 4, 11, 13]. We describe Datalevin's version because it defines the
units whose cardinalities are estimated and the physical paths whose
directional costs are compared.

### 3.2 Plan enumeration

Datalevin uses a Selinger-style dynamic program over connected subsets of each
query-graph component. It produces left-deep trees because each indexed
expansion requires a base relation and because star collapse leaves graphs that
are often chain-like. Disconnected components are planned independently,
executed concurrently, and combined in estimated-size order.

Exhaustive dynamic programming is valuable for small graphs but its search
cost can dominate planning for generated or unusually broad queries. The
enumerator therefore monitors the number of candidate plans. Once a configurable
budget is exceeded, it retains the lowest-cost representative for each
unordered subset and continues greedily. This dynamic exhaustive-to-greedy
transition spends search effort according to the graph encountered rather than
a fixed query-size cutoff. [**Add planning-state and switch-point measurements
from the evaluation instrumentation.**]

### 3.3 Physical alternatives

The cost model chooses among physical methods rather than merely permuting
logical joins:

- A forward reference can feed target entity IDs directly into a merge scan.
  A reverse reference probes AVE to recover source entity IDs. Equal ordinary
  values use a related indexed lookup.
- Reverse-reference and value-equality edges may instead use a hash join. A
  bitmap built from the input provides sideways information passing to filter
  the other scan before hashing, reducing both tuples and memory.
- If a degree-one target exists only to test existence and contributes no
  required output, an indexed semi-join emits each input tuple once rather than
  materializing its fanout.
- Datalog-specific `or-join` and selected `not-join` forms receive dedicated
  planning and filtering behavior. Multiple recursive rule branches can expose
  join links after rule resolution, while preserving their declared join
  variables.

Planning and execution are pipelined. Components can be planned in parallel,
and execution batches begin without requiring the entire query result to be
materialized at every boundary.

## 4. Evaluation

We ask four questions:

**Q1.** Is the complete system competitive on a difficult, established join
ordering workload? **Q2.** How much do direct counts and query-local sampling
each contribute? **Q3.** Do estimates track actual cardinalities closely enough
to select robust plans? **Q4.** What planning cost does this evidence and
enumeration impose?

### 4.1 Setup and end-to-end result

We use the Join Order Benchmark, whose 113 queries were designed to expose
cardinality-estimation and join-order failures on a real, highly correlated
IMDB snapshot. We translated its schema and queries to Datalevin Datalog and
manually checked result equivalence with the SQL workload. The Datalevin
database contains 277,878,411 datoms and occupies 17 GB.

The current run used a November 2023 16-inch MacBook Pro with an Apple M3 Pro
(six performance and six efficiency cores), 36 GB memory, and a 1 TB SSD.
PostgreSQL 18 and Datalevin used their default configurations. Each system
received one warm-up pass followed by one measured pass over all queries;
reported times come from each system's explain facility and exclude client
startup and communication. This one-pass protocol stresses plan robustness
across the workload but does not characterize run-to-run variance; the final
evaluation will add repeated, interleaved passes.

| System | Planning (s) | Execution (s) | Total (s) | Completed |
|---|---:|---:|---:|---:|
| PostgreSQL 18 | 1.043 | 170.286 | 171.329 | 113/113 |
| Datalevin | 6.605 | 65.198 | 71.803 | 113/113 |

Datalevin's measured total is 2.39× lower despite spending more time in
planning. This result establishes that the implemented design works at scale;
it does not isolate which optimizer ideas cause the difference.

### 4.3 Estimation quality and case studies

Instrumentation records an estimated and actual output cardinality at each
materialized plan boundary. For nonzero actual cardinality \(a\) and estimate
\(e\), we report q-error `max(e/a, a/e)`; zero cases are reported in separate
false-empty and false-nonempty categories. We aggregate median, 90th, 95th, and
maximum q-error by base star, directional edge, and complete component. We also
report plan regret where feasible by replaying alternative plans on a selected
subset, rather than treating q-error alone as a proxy for runtime.

Three query case studies will connect estimates to decisions:

1. a selective point or range predicate for which an exact index count changes
   the starting relation;
2. a forward/reverse relationship whose fanout differs sharply by direction;
3. a skewed relationship for which variance correction changes the chosen
   start or join method.

### 4.4 Expected limitations

The current evaluation uses one data model and one complex analytical
workload. JOB is valuable because of its correlations and established use in
optimizer research, but it does not cover updates, recursive rules, or
application-style point queries. The comparison also contrasts complete
systems and data representations, not isolated optimizers. We therefore use
PostgreSQL as an external credibility check and rely on Datalevin ablations for
causal claims. We will report database size, load and analysis time, exact
versions, JVM settings, thermal controls, and raw per-query results in the
artifact.

## 5. Related Work

Selinger et al. established dynamic-programming join enumeration and
cost-based access-path selection [14]. Later work improved enumeration for
connected subgraphs and studied the tradeoff among estimation, cost models,
and search [7, 12]. Datalevin adopts this foundation but applies it after
entity-star collapse and changes search policy dynamically when enumeration
exceeds a plan budget.

RDF optimizers exploit characteristic sets and query graph structure to
estimate and order multi-pattern queries [4, 11, 13]. Pivot scans similarly
retrieve multiple attributes without a sequence of self-joins [2].
Datalevin's entity stars and merge scans build on these insights, specialized
to explicit entity IDs, typed reference attributes, and nested EAV storage.

Sampling has long been used for join selectivity [5], including index-based
join sampling evaluated on JOB [9]. Bayesian estimators combine sparse
observations with prior knowledge [6]. Datalevin's distinction is an integrated
systems point: the same ordered structures support current counts, rank-based
sampling, directional execution, and cost estimation, while a durable
fallback absorbs query-local sample uncertainty. Bitmap sideways-information
passing follows the broader family of pragmatic join filters [15].

## 6. Conclusion

Datalevin demonstrates that EAV flexibility need not preclude conventional
cost-based discipline. Countable ordered indexes answer marginal cardinality
questions at plan time; query-local samples address correlations and
directional fanout; and shrinkage moderates sparse, skewed observations. The
initial JOB result—71.8 seconds for all 113 queries over 277.9 million
datoms—shows that the combined system is practical. The remaining evaluation
will determine how much each source of cardinality evidence contributes, where
estimates still fail, and whether the extra planning time reliably buys
execution-time robustness.
