# TPC-H Benchmark

This benchmark runs a TPC-H-style analytical workload against Datalevin, SQLite,
and PostgreSQL on identical data. TPC-H is the standard decision-support
benchmark: 22 ad-hoc queries over a normalized 8-table schema. It complements
the [Join Order Benchmark](../JOB-bench), whose queries are deliberately harder
than the TPC series, by measuring the more ordinary analytical workload.

> **Derived, not audited.** These results are TPC-H-style. They follow the
> published data and query definitions but are not audited TPC-H results and
> must not be presented as official. See the [TPC fair-use
> rules](https://www.tpc.org/information/other/policy_fair_use5.asp).

## Scope and data set

The schema is the TPC-H schema (region, nation, part, supplier, partsupp,
customer, orders, lineitem). Data is generated by the reference `dbgen` tool at
a chosen scale factor (SF). SF0.01 is a quick smoke scale (~9 MB); SF1 is the
standard 1 GB scale (~6M lineitem rows).

All three systems load the same pipe-delimited `.tbl` files, so every comparison
runs on identical values. The benchmark inherits Datalevin's native dependencies
from the local checkout. Rebuild working databases from these files when moving
between incompatible native storage versions.

## Setup

Build `dbgen`/`qgen` and generate data:

```bash
scripts/fetch-dbgen.sh          # downloads and builds dbgen/qgen (pinned revision)
scripts/generate-data.sh 1      # SF1; use 0.01 for a smoke run
```

`data/tbl/` is git-ignored. Query files are committed; regenerate them with
`scripts/generate-queries.sh` only when intentionally refreshing the query set.

## Queries

The canonical query substitutions are produced by `qgen -d` (the reference
default substitution values) and committed under `queries/standard/`. Two
dialect-specific copies are maintained:

- `queries/postgres/N.sql` — ANSI/PostgreSQL
- `queries/sqlite/N.sql` — SQLite (ISO date strings, `substr` for `extract`,
  Q15 as a CTE)
- `src/datalevin_tpch/queries.clj` — the Datalevin Datalog translation (`q-N`)

Dates are stored as ISO-8601 strings so range predicates compare correctly
lexicographically. Date arithmetic in the SQL is precomputed to literal bounds
that match the fixed default substitutions, e.g. Q1's
`l_shipdate <= date '1998-12-01' - interval '90' day` becomes `"1998-09-02"`.

TPC-H §2.1.2.9 requires a result row limit on Q2 (100), Q3 (10), Q10 (20),
Q18 (100), and Q21 (100). `qgen` emits these as the `ROWS_FETCH` directive,
which is only a comment in portable dialects, so `scripts/generate-queries.sh`
restores each one as a real `LIMIT` clause and the Datalog translations carry
the matching `:limit`. The committed query files and `queries.clj` are checked
by the test suite.

## Running

Run all commands from this directory.

### Datalevin

```bash
clj -X:datalevin-db                              # load data
clj -X:datalevin-bench '{:queries :all :out "datalevin_pass.csv"}'
```

### SQLite (the local reference)

```bash
clj -X:sqlite-db
clj -X:sqlite-bench '{:queries :all :out "sqlite_pass.csv"}'
```

### PostgreSQL (requires a server)

```bash
clj -X:pg-db  '{:url "jdbc:postgresql://localhost:5432/postgres"}'
clj -X:pg-bench '{:url "jdbc:postgresql://localhost:5432/postgres"}'
```

Connection settings can also come from the `pg.url`, `pg.user`, and `pg.pass`
JVM properties.

## Verification

SQLite is the local correctness oracle. `clj -X:verify` runs every Datalevin
Datalog translation and the corresponding SQLite query, then compares columns
according to their meaning. Identifiers, projected values, counts (including
Q12's conditional counts), and Q1/Q18 quantity sums must match exactly. Other
monetary aggregates, averages, and ratios retain a relative rounding tolerance
of `1e-6`. Numeric normalization preserves integer precision. Before comparing
contents, verification checks the output width and each backend's required
ordering and the required row limit. For limited queries, the oracle removes
only the final SQL `LIMIT` so every eligible boundary-tie row remains available.
A different selection of tied rows is valid only when every complete row and
its multiplicity exist in that oracle; matching sort keys alone is insufficient.
Both databases must already exist, and all eight nonempty table counts must
agree before query verification begins:

```bash
clj -X:verify '{:queries :all :out "verification.edn"}'
clj -X:verify '{:queries [1 6] :dump? true}'   # print both sides on mismatch
clj -X:verify '{:queries :all :timeout-ms 120000 :out "verification.edn"}'
```

The EDN report is updated after each query and records table counts, runtime
versions, result counts, and diagnostic wall times. These validation timings
include preparation and result consumption; they are not benchmark passes.
`:timeout-ms` sets each native query's deadline. For automation without process
exit, call `datalevin-tpch.verify/run-verification`; the CLI exits nonzero when
any query fails, after closing the databases.

All 22 queries pass at SF0.1 and SF1 with the current verifier. The
[validation report](../../doc/measurements/tpch-validation-2026-10-26.md) retains
the input hashes, per-query reports, and paired Q18 performance checks.
Because the oracle is SQLite, the runner enables
`PRAGMA case_sensitive_like=ON`: SQLite's `LIKE` is case-insensitive for ASCII
by default, whereas TPC-H and PostgreSQL are case-sensitive.

## Methodology

- Data generation, loading, index creation, correctness checks, and warmup are
  outside the measured interval.
- SQLite uses WAL and a 1 GiB memory map for reads.
- On macOS the harness pauses the current user's `mediaanalysisd` and
  `photoanalysisd` with `SIGSTOP` for the measured interval and resumes exactly
  those processes with `SIGCONT` afterward. A daemon that was already stopped is
  left alone. The control is a no-op on other platforms or where the signal is
  not permitted.
- PostgreSQL timings come from `EXPLAIN (ANALYZE, FORMAT JSON)` planning and
  execution times, matching the JOB-bench protocol.
- SQL `ORDER BY` and matching Datalog `:order-by` clauses run inside the timed
  query, with identical sort keys and directions across all three backends.
- Datalevin wall time covers the complete `d/q` or `d/explain` call and result
  consumption. With `:explain? true`, execution time is wall time minus reported
  preparation time, including final sorting and explain overhead. The engine's
  execution counter can stop before sorting on some query paths.
- Publishable results should use one warmup pass followed by one measurement
  pass in separate JVM processes, and a fixed data set, seed, and machine.

## Translation notes

The Datalog translations are single queries in every case. Several TPC-H
patterns required care:

- **Aggregation and `:with`.** Datomic-style Datalog projects away variables not
  in `:find`, so `(sum ?x)` can collapse duplicate values. Queries that sum a
  derived value add `:with` over the lineitem entity to preserve row
  multiplicity. Verified against SQLite.
- **Grouped subqueries** (Q2, Q17, Q20) compute a relation once and join it by
  part key, or part/supplier key. They restrict aggregation to eligible parts
  and suppliers while retaining every relevant lineitem. Nested `q` calls
  receive only the database; no outer row values are passed as scalar inputs.
- **`GROUP BY ... HAVING`** subqueries (Q11, Q18) are expressed as nested
  grouped relations. Q18 applies its quantity threshold inside the nested
  query and returns the computed sum, so only qualifying orders cross into
  the outer query.
- **`LEFT OUTER JOIN`** (Q13) uses two mutually exclusive `or-join` branches:
  one grouped count relation joined to customers, and a `not` branch binding
  zero for the rest.
- **`CASE` over aggregates** (Q8, Q14) is expressed with `:with` and nested
  aggregates; `if` is not resolvable inside nested queries.
- **`extract(year ...)`** becomes `(subs date 0 4)` plus `parse-long`.
- **`LIKE`** uses native `like`/`not-like`, including Q13's
  `%special%requests%` comment filter. Matching is case-sensitive; `%` also
  matches newlines and `_` matches one Unicode character. The benchmark tests
  compare these predicates with case-sensitive SQLite `LIKE`. Changing the
  expressions in `queries.clj` requires rerunning the SQL gate.

## Results

Current evidence includes complete correctness checks at SF0.1 and SF1,
a diagnostic SF1 profile, and isolated Q18 before/after timings. See the
[validation and performance report](../../doc/measurements/tpch-validation-2026-10-26.md).
The [hotspot follow-up](../../doc/measurements/tpch-hotspots-2026-10-26.md)
records verified SF1 improvements for Q1, Q13, and Q19. Q13 groups qualifying
orders once, Q19 exposes selective brand branches, and Q1 reduces tuple and
aggregation allocations. Run the benchmark commands above for a complete timing
comparison on your machine.

The [LIKE correctness follow-up](../../doc/measurements/like-correctness-2026-10-26.md)
records the matcher fixes, SQL oracle tests, and repeated SF0.1/SF1 gates with
Q13 restored to native `not-like`. Its isolated Q13 comparison shows performance
comparable to the regex workaround.

The [second Q1/Q18 optimization pass](../../doc/measurements/tpch-q1-q18-2026-10-27.md)
adds direct grouped reduction when native schema and retained entity keys prove
the aggregate input distinct. Q1 also uses faster scalar-binding copies; Q18
filters its groups before returning the nested relation. The report retains
complete SQL gates and repeated SF1 before/after measurements.

The [Q1/Q18 follow-up on 1.2.10](../../doc/measurements/tpch-q1-q18-2026-10-28.md)
reduces entity sorting costs and compiles HAVING before filtering groups.
SF1 paired medians improve from 7.03 to 5.78 seconds for Q1 and from 3.38 to
2.58 seconds for Q18; all 22 queries still pass at SF0.1 and SF1.

The [SF1 three-engine comparison](../../doc/measurements/tpch-engine-comparison-2026-10-28.md)
checks all 22 queries on Datalevin, SQLite, and PostgreSQL, then records three
fully consumed wall-time samples per query after warmup. Summed medians are
28.42, 22.01, and 7.51 seconds respectively. Q1, Q13, Q21, Q7, and Q18 account
for most of the gap to PostgreSQL. The report includes an interactive chart,
raw samples, PostgreSQL plans, and replay scripts. Some SQL samples overlap
other JVM work; small differences need confirmation. Its PostgreSQL wall-time
protocol differs from the server-only EXPLAIN times emitted by `:pg-bench`.

The [grouped-query follow-up](../../doc/measurements/tpch-decorrelation-2026-10-28.md)
replaces correlated aggregate calls in Q2, Q17, and Q20 with grouped relations.
Focused SF1 paired medians improve by 2.77×, 2.41×, and 2.35×; all 22 queries
pass again at SF0.1 and SF1. The three-engine table records the earlier forms.

The raw CSVs (`datalevin_pass.csv`, `sqlite_pass.csv`, `postgres_pass.csv`) and
`results.edn`-style manifests should be retained alongside any published table,
together with the machine, JVM, database versions, and scale factor.
